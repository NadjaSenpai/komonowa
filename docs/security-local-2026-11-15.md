## SEC-LOCAL-001：ログイン後の再認証に試行回数制限がない

**優先度：中（暫定、既存セッションの取得が前提）。2026-11-15に修正済み。以下の再現結果は修正前の記録。**

対象：

- `POST /api/auth/email`：`worker/routes/profile.ts:48`
- `POST /api/auth/password`：`worker/routes/auth.ts:225`
- `POST /api/auth/withdraw`：`worker/routes/auth.ts:211`

現在のパスワードを照合する処理が、ログイン用の `takeAttempt` 等を経由せず実行される。
各ルートにログイン済みメンバーで異なる誤パスワードを逐次12回送信したところ、全12回が403で、429にはならなかった。
コード確認でもこの3処理に試行制限がないことを確認した。大量リクエストによる検証は実施していない。

再現方法（隔離環境のみ）：

1. 管理者を作り、招待経由でメンバーを登録してログインする。
2. そのセッションで対象APIへ誤った `currentPassword` を12回送る。
3. メール変更では検証用 `email`、パスワード変更では有効な長さの `newPassword` も指定する。
4. すべて403になることを観測する。認証なしでのバイパスは確認していない。

セッションを奪った攻撃者が、ログイン側の試行制限を経由せず現在のパスワードをオンライン推測できる。推測に成功するとパスワードやメールの変更・退会へ進める可能性がある。今回、実際のパスワード解読やアカウント乗っ取りは実証していない。

推奨修正：利用者ID単位で3ルート共通の再認証試行制限を設ける。並列試行に強い既存の `worker/attempts.ts` を再利用し、一定回数の失敗後は429にする。成功時の解除と時間窓、通常ログインへの影響を設計したうえで、3ルート間の迂回と並列試行の回帰テストを追加する。

初回の観測テスト3件は、超過分429を期待する回帰テストに置き換えた。

### 修正内容と再検証

- `worker/reauth.ts` に共通処理を追加。メール変更・パスワード変更・退会で利用者ID単位に15分間・10回の試行枠を共有し、超過分は照合前に429にする。
- 新規マイグレーション `0012_reauth_failures.sql` で通常ログインとは独立したテーブルを追加。正しいパスワードで再認証すると失敗記録を解除する。
- 3ルートごとの制限、ルート／セッション変更での迂回防止、別利用者・通常ログインへの影響がないこと、30並列で10件403・20件429、15分経過後の復帰、成功時の解除を確認。
- 修正前に回帰テスト7件が失敗することを確認し、修正後は監査テスト15件すべてが通過した。
- 修正後の `npm run check` も成功（型検査・26ファイル221テスト・本番ビルド）。ローカルD1に0012を適用し、実HTTPでも3操作合計10回の失敗後に各ルートが429になることを確認した。実HTTP検証は計27件の期待ステータスが一致した。
- デプロイ時は既存のマイグレーション手順で0012を適用する。本番環境は今回の作業対象外。
