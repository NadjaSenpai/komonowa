# ページ間リンク（`[[タイトル]]`）設計

## 目的

Cosense（Scrapbox）のように、本文で `[[タイトル]]` と書くだけで記事同士がつながり、まだない記事へのリンクからその記事を書き始められるようにする。記事を開くと、その記事にリンクしている記事（被リンク）も見える。書きながらページが育っていく体験が目的。

## 範囲

- やる
  - 段階1：`[[タイトル]]` をリンクとして描画する。リンク先がない記事は見た目を変え、押すとそのタイトルで新規作成画面を開く
  - 段階2：記事の下に「このページにリンクしているページ」を表示する
  - 前提として、記事タイトルを重複禁止にする
- やらない
  - タイトル変更時に、ほかの記事の `[[旧タイトル]]` を書き換えること（段階3）。変更後、旧タイトルへのリンクは「まだない記事」になる
  - 2ホップリンク、`[[` 入力時のタイトル補完（段階4）。ただし段階4をこの設計の上に作れるようにしておく
  - 古い版（`revisions`）の本文のリンク解析
- 避けたいこと
  - メンバーに理由の見えないエラーを出すこと。たとえば、ごみ箱の記事がタイトルを確保しているせいで作成できない、という状態は作らない

## 決まったこと

- 記法は `[[タイトル]]`。Markdown のリンク（`[文字](url)`）やチェックボックス（`[ ]`）とぶつからないよう、二重角かっこにする
- タイトルは、ごみ箱に入っていない記事の中で重複禁止。ごみ箱の記事はタイトルを確保しない
- リンクは保存時に解析して表に書き出す（下の「方式」の案2）
- 本番には現在記事がないため、既存データの重複解消やリンクのバックフィルは不要

## 方式

| 案 | 内容 | 判断 |
|---|---|---|
| 1. その場で文字列検索 | 表示のたびに本文から `[[…]]` を拾い、被リンクは `instr` で探す | 不採用。SQLite の `lower()` は ASCII にしか効かず、全角・半角の揺れを吸収できない。コード内の `[[…]]` も数えてしまう。段階4で作り直しになる |
| 2. 保存時に表へ書き出す | 作成・編集・復元時に本文を解析し、`article_links` に書く | **採用**。正規化をサーバー側でそろえられ、コードを除外でき、段階4の土台になる |
| 3. リンク先を記事 ID で書く | `[[<id>]]` | 不採用。手で書けず、Cosense らしさがなくなる |

## 設計

### タイトルの正規化キー

「同じタイトル」は次の手順で作るキーで判定する。タグの扱い（NFKC、大文字小文字を区別しない）に合わせたもの。

1. 前後の空白を除く
2. NFKC 正規化
3. 連続する空白を半角スペース1つにまとめる
4. `toLowerCase()`（JS 側で行うので英字以外の大文字小文字にも効く）

表示するタイトル（`articles.title`）は、入力どおりのまま保存する（前後の空白だけ除く）。キーはサーバーで計算し、クライアントから受け取らない。

### スキーマ（新しいマイグレーション `0004_wiki_links.sql`）

- `articles.title_key TEXT NOT NULL`：上のキー
- 一意インデックス `articles(title_key) WHERE deleted_at IS NULL`：ごみ箱の記事はタイトルを確保しない
- `article_links(source_id TEXT NOT NULL REFERENCES articles(id) ON DELETE CASCADE, target_key TEXT NOT NULL, PRIMARY KEY (source_id, target_key))`
- インデックス `article_links(target_key)`：被リンクの検索用

既存の行はないので、`title_key` は `lower(trim(title))` で埋めればよい（念のための初期値で、正確な NFKC は不要）。

### リンクの解析

- `[[` と `]]` で囲まれた、改行と `[` `]` を含まない、空でない文字列をリンクとする。前後の空白は除き、200文字（タイトルの上限）を超えるものはリンクにしない
- インラインコードとコードブロックの中は対象外
- Markdown の解析には、すでに使っている `marked` のトークン（lexer）を使い、描画と解析で同じ判定にする。同じ処理をクライアント（描画）とワーカー（解析・正規化）の両方で使う
- 同じ記事内の重複リンクは1件にまとめる。自分自身へのリンクも保存はする（被リンクの表示で除く）

### 保存時の書き込み

`worker/routes/articles.ts` の `writeStatements` が、履歴とタグを1つのバッチで書いている。ここで同じように、この記事の `article_links` を消して書き直す。対象は作成・編集・版の復元のすべて。既存の「`revision_id` が今回の版であること」という条件にそろえ、競合したときには何も書かないようにする。

### タイトルの重複エラー

- 作成・編集・版の復元で、ほかの（ごみ箱でない）記事とキーがぶつかったら `409`。メッセージは「同じタイトルの記事がすでにあります」。版の競合の `409` とは、`current` があるかどうかで区別する（クライアントの既存処理のまま）
- 管理者がごみ箱から戻すとき（`POST /admin/trash/:id/restore`）にぶつかったら `409`。メッセージは「同じタイトルの記事がすでにあります。どちらかのタイトルを変えてから戻してください」
- 一意インデックスが最後の砦になる。事前チェックとの間に割り込まれて制約違反が起きた場合も、500 ではなく同じ `409` を返す

### API

- `GET /api/articles/by-title/:title`：キーで引いて `{ id }` を返す。なければ `404`。認証は既存の記事 API と同じ（`requireAuth`）
- `GET /api/articles/:id` のレスポンスに次の2つを足す
  - `links`：本文中のリンク先ごとの `{ key, id | null }`。リンク先の有無の表示に使う
  - `backlinks`：この記事のキーへリンクしている、ごみ箱でない記事の `{ id, title, updated_at }`。自分自身は除き、更新日の新しい順

### 画面

- 描画：`renderMarkdown` で `[[タイトル]]` を `<a href="/wiki/<タイトル>" class="wikilink">タイトル</a>` にする。URL のタイトルは `encodeURIComponent` で符号化する（`/` や `?` を含むタイトルのため）。表示・プレビュー・履歴のどこでも同じ
- ルート `/wiki/:title`：`by-title` で引き、あれば `/articles/<id>` に、なければ `/articles/new?title=<タイトル>` に置き換えて移動する
- 記事の表示画面では、`links` を使ってリンク先のない `wikilink` に `missing` クラスを付け、見た目を変える（Cosense の未作成リンクのように薄い色にする）。プレビューと履歴では色分けしない
- 新規作成画面は `?title=` があればタイトル欄に入れておく
- 本文内のアプリ内リンク（`/` で始まるリンク）は、クリックを拾ってページを再読み込みせずに画面遷移する
- 被リンクは本文と添付の間に、記事のカード一覧として出す。0件なら何も出さない

```
┌ 記事タイトル ───────────────────────┐
│ 本文 … [[手順書]] … [[まだない記事]] │  ← 後者は薄い色
├ このページにリンクしているページ ────┤
│ ▸ 障害対応メモ        11/14 更新     │
│ ▸ 新人向けまとめ      11/12 更新     │
├ 添付ファイル ────────────────────────┤
```

### テスト

- 記事 API：作成・編集・版の復元で、正規化して同じになるタイトル（例：`Docker` と `ｄｏｃｋｅｒ`）が `409` になる。ごみ箱の記事と同じタイトルは作れる。ごみ箱から戻すときにぶつかると `409`
- リンク：`links` にリンク先の有無が正しく入る。コード内の `[[…]]` は数えない。編集でリンクを外すと被リンクから消える。ごみ箱の記事は被リンクに出ない。自分自身は出ない
- `by-title`：未ログインは `401`、メンバーと管理者は引ける、ない記事は `404`、ごみ箱の記事は `404`
- 解析と正規化の関数の単体テスト（`src/__tests__/` に）

## 実装する人に任せること

- 解析・正規化の共通コードをどこに置くか（`worker` と `src` の両方の tsconfig から読める場所。たとえば新しく `shared/` を作る）
- `wikilink` と `missing` の具体的な色。既存の `styles.css` の配色に合わせる
- 被リンクのカードの細かい見た目。既存の記事一覧のスタイルを使ってよい
