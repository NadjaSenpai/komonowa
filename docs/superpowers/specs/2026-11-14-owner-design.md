# 所有者（短い設計）

## 目的

管理者を増やしたい。そのとき、ほかの管理者に最初の管理者が締め出されないようにする。

## 締め出しの経路と対策

| 経路 | 今 | 対策 |
| --- | --- | --- |
| 権限をメンバーに下げる | できる | 所有者には 403 |
| 無効化する | できる | 所有者には 403 |
| パスワード再設定メール | 本人のアドレスにしか届かない | そのまま |
| メールアドレス・名前の変更、利用者の削除 | API がない | そのまま |

## 決めたこと

- `users.is_owner`（0/1）を足し、ユニークな部分インデックスで所有者を1人に限る（マイグレーション `0005`）。既存データでは、いちばん最初に作られた管理者を所有者にする。
- `/api/auth/setup` で作る最初の管理者は所有者。
- `PATCH /api/admin/users/:id`：相手が所有者なら 403「所有者の権限変更や無効化はできません」。所有者本人は今まで通り自分の権限を変えられないので、所有者はいつも有効な管理者。「有効な管理者が1人以上」の条件付き UPDATE は念のため残す。
- `GET /api/admin/users` は `is_owner` を返す。管理画面では所有者の権限欄を「所有者」の文字にし、「無効化」ボタンを出さない。「再設定メールを送る」は残す。
- 所有者の譲渡は画面に作らない。`docs/operations.md` に `wrangler d1 execute` の手順（今の所有者を外す → 新しい所有者に付ける）を書く。

## やり方の比較

- 採用：所有者の印を列として持つ。手で譲っても正しく、1人だけをデータベースで守れる。
- 不採用：いちばん古い管理者を毎回計算する。手で譲ると合わなくなり、1人だけの保証もない。
- 不採用：画面での譲渡（B）。めったに使わず、うっかり譲る事故を避けたい。

## 作らないもの

- 所有者だけができる操作（管理者の任命など）。ほかの管理者どうしは今まで通り下げ合えるが、所有者が戻せる。
